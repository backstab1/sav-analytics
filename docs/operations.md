# Эксплуатация sav-analytics

Runbook production-контура (P6): из чего он состоит, как его развернуть,
обновить, откатить, восстановить из копии и что делать при сбоях.
Архитектурные решения — в [architecture.md](architecture.md), порядок работ —
в [roadmap.md](roadmap.md).

## 1. Контур

`compose.yaml` в корне репозитория поднимает:

| Сервис | Что делает | Проверка здоровья |
| --- | --- | --- |
| `proxy` | Caddy: HTTPS, перенаправление с HTTP, предел тела запроса, `/metrics` наружу не отдаёт | — |
| `api` | FastAPI, два процесса uvicorn; только ставит задания | `/api/health` в образе, `/api/ready` у прокси |
| `worker` | `sav-analytics-worker`: сборки отчётов и импорт, по процессу на задание | `sav-analytics-worker --check` |
| `migrate` | `sav-analytics migrate`, разовый шаг перед стартом api и worker | — |
| `postgres` | метаданные: проекты, история, задания, версии отчётов, пользователи, журнал | `pg_isready` |
| `backup` | профиль `backup`, запускается по расписанию | — |

Файлы проектов — исходные SAV, волны, книги — лежат в томе `sav_data`
(`/data`), метаданные — в PostgreSQL. Резервная копия берёт и то, и другое.

Контейнеры приложения работают от пользователя `app` (uid 10001), с файловой
системой только для чтения (запись — в `/data` и `/tmp`), без capabilities и
с `no-new-privileges`. Пределы ресурсов заданы в `deploy.resources.limits`.
Политика перезапуска — `unless-stopped`.

## 2. Первый запуск

Сервер: Ubuntu LTS, Docker Engine с плагином compose, DNS-имя, указывающее
на сервер (`architecture.md` §4).

```sh
sudo mkdir -p /opt/sav-analytics && cd /opt/sav-analytics
# compose.yaml, deploy/ и scripts/ — из репозитория (git clone или копия).
cp .env.example .env            # заполнить, см. ниже
mkdir -p secrets backups
openssl rand -base64 48 > secrets/backup_passphrase   # хранить ещё и вне сервера!
chmod 600 .env secrets/backup_passphrase
docker compose pull
docker compose up -d
docker compose exec api sav-analytics create-user admin --admin
```

Обязательные переменные `.env`: `POSTGRES_PASSWORD`, `SAV_DOMAIN`. Прочие
настройки приложения — `SAV_ANALYTICS_*` из `src/sav_analytics/settings.py`.
Для внутреннего имени без выхода в интернет в `deploy/Caddyfile` включается
`tls internal`.

Проекты прежнего файлового хранилища переносятся командой
`sav-analytics import-legacy`; сначала `--dry-run` — он проверяет перенос на
копии данных и ничего не меняет.

## 3. Обновление и откат

Каждый коммит в `main` собирает образ `ghcr.io/<репозиторий>:<sha>`
(`.github/workflows/deploy.yml`). Развёртывание — вручную, через «Run
workflow»: окружение `staging`, затем `production` с тем же тегом.

`deploy/deploy.sh` на сервере:

1. тянет образ;
2. выполняет миграции отдельным шагом;
3. перезапускает `api`, `worker`, `proxy`;
4. ждёт `/api/ready` до 120 секунд и при неудаче возвращает прежний образ.

**Откат вручную** — тот же workflow с прежним тегом (он записан на сервере в
`.deployed-previous`) или `./deploy/deploy.sh <образ:прежний-тег>`.

### Миграции и откат

Миграции только добавляют таблицы и колонки, поэтому прежний образ работает
поверх новой схемы, и откат приложения не требует отката базы. Миграция,
которая удаляет или переименовывает, выкатывается в два выпуска: сначала код,
который не пользуется старым, затем удаление. Документ проекта мигрирует при
чтении; перед первой перезаписью новой схемой его копия кладётся в
`project_backups` (roadmap, «Устройство, которое не меняется»).

### Staging

Staging — тот же `compose.yaml` на отдельной машине со своим `.env` и своим
`SAV_DOMAIN`. Данные production туда не копируются; для проверки берутся
эталонные наборы из `scripts/benchmark.py` и `tests/golden`.

## 4. Задания

Очередь — таблица `jobs` в PostgreSQL (`src/sav_analytics/jobs/queue.py`):

- две одинаковые сборки одной версии конфигурации — одно задание;
- worker держит задание арендой и продлевает её пульсом; умерший worker
  отпускает задание по истечении аренды (60 с), и его подбирает другой;
- задание дольше `SAV_ANALYTICS_REPORT_TIMEOUT_SECONDS` (30 мин) убивается и
  проваливается с `JOB_TIMEOUT`;
- процесс задания, убитый за память (`JOB_MEMORY_LIMIT_MB`), повторяется,
  пока не кончатся попытки, затем `WORKER_CRASHED`;
- при свободном месте меньше `MIN_FREE_DISK_MB` worker не берёт задания;
- завершённые задания удаляются через `JOB_TTL_DAYS` (30 дней).

Число одновременных тяжёлых заданий — `WORKER_CONCURRENCY` (2). Чтобы
добавить мощности, запускают второй контейнер `worker`:
`docker compose up -d --scale worker=2`.

## 5. Наблюдение

- **Журналы** — JSON в stdout каждого контейнера (`docker compose logs`):
  `request_id` связывает ответ API с записью журнала, `job_id` и `project_id`
  — задание и проект. Строк респондентов в журнале нет.
- **Метрики** — `GET /metrics` с `Authorization: Bearer $SAV_ANALYTICS_METRICS_TOKEN`
  изнутри сети: запросы и время ответа, задания по статусам, возраст самого
  старого задания в очереди, длительность и сбои заданий за сутки, число
  проектов, объём тома.
- **Журнал аудита** — в интерфейсе: личный кабинет (`/account.html`) →
  «Журнал действий» (только администратор), или `GET /api/admin/audit`.
- **Пользователи** — там же, «Пользователи»: добавить, отключить, задать
  новый пароль. Роль в интерфейсе не назначается: новые учётные записи —
  аналитики, администратора заводят на сервере
  (`sav-analytics create-user <имя> --admin`).

### Рекомендуемые оповещения

| Условие | Значит |
| --- | --- |
| `sav_queue_oldest_seconds > 900` | worker не берёт задания: упал, занят или кончилось место |
| рост `sav_job_failures_24h{code="WORKER_LOST"\|"WORKER_CRASHED"}` | worker падает — память, OOM killer, перезапуски |
| `sav_job_failures_24h{code="JOB_TIMEOUT"} > 0` | отчёт дольше 30 минут — профилировать |
| `sav_job_duration_seconds_max_24h{kind="report.build"} > 120` | нарушена цель architecture.md §4.2 |
| контейнер `worker` unhealthy | цикл worker не отмечался 2 минуты |
| `/api/ready` отвечает 503 | нет базы, схема не та или том не пишется |
| нет строки `OK` в `backups/backup.log` за сутки | резервная копия не сделана |

## 6. Резервное копирование

Ежедневно (cron на хосте):

```cron
30 2 * * * cd /opt/sav-analytics && docker compose --profile backup run --rm backup && rclone sync backups remote:sav-backups
```

`scripts/backup.sh` делает дамп PostgreSQL и архив тома, шифрует их gpg
(AES256) парольной фразой из `secrets/backup_passphrase`, **проверяет**
копию — расшифровку, суммы, `pg_restore --list`, `tar -t` — и только потом
пишет `OK` в `backups/backup.log`. Копии старше 14 дней удаляются.
Копия должна уехать с сервера (`rclone`, `rsync` на другой хост) — иначе
она не защищает от потери сервера. Парольная фраза хранится отдельно от
копий: без неё копии не восстановить.

RPO — не более 24 часов (ежедневная копия), RTO — не более 4 часов.

### Ежемесячная проверка восстановления

```sh
docker compose --profile backup run --rm --entrypoint restore.sh backup /backups/<копия>.tar.gpg
```

Пробное восстановление разворачивает дамп во временную базу и том — во
временный каталог, сверяет суммы, считает проекты и проверяет, что у
каждого есть исходник, печатает время и всё убирает. Результат и время
записываются в журнал проверок (дата, копия, число проектов, время).

### Настоящее восстановление

1. `docker compose stop api worker`
2. Пустая база и пустой том: `docker compose down`, удалить тома
   `pg_data` и `sav_data` (**только убедившись, что копия проверена**),
   `docker compose up -d postgres`.
3. `docker compose --profile backup run --rm --entrypoint restore.sh backup /backups/<копия>.tar.gpg --into-empty`
   — скрипт откажется работать с непустой базой или томом.
4. `docker compose up -d`, проверить `/api/ready` и вход.

## 7. Удаление данных

Проект из библиотеки сначала попадает в корзину и восстанавливается
30 дней (`TRASH_RETENTION_DAYS`). Окончательно удаляет:

- администратор — «Удалить навсегда» (`DELETE /api/admin/trash/{id}`);
- ежедневная очистка: `docker compose exec api sav-analytics purge-trash`
  (cron), удаляет пролежавшие в корзине дольше срока.

Удаление убирает запись проекта, историю, задания, версии отчётов и
каталог с SAV и книгами; в журнале аудита остаётся событие без данных.
Проверка: после удаления `GET /api/projects/trash` не содержит проекта, а
каталога `/data/projects/<id>` нет. Из резервных копий проект уходит по
истечении их срока хранения (14 дней).

## 8. Инциденты

1. **Не открывается сайт.** `docker compose ps` — что не healthy;
   `docker compose logs --tail 200 proxy api`. `/api/ready` покажет, что
   именно не готово: база, схема или том.
2. **Сборки стоят «в очереди».** `docker compose logs worker`; метрика
   `sav_queue_oldest_seconds`; место на диске; `docker compose restart worker`
   — брошенные задания вернутся в очередь сами.
3. **Подозрение на компрометацию учётной записи.** Администратор отключает
   пользователя (сессии закрываются сразу) и смотрит журнал аудита по
   пользователю: что читал и скачивал. Затем новый пароль.
4. **Ошибка выпуска.** Откат на прежний тег (§3). База совместима.
5. **Потеря сервера.** Новый сервер по §2, восстановление по §6 из копии
   вне сервера, перенаправление DNS.

После инцидента — запись: что случилось, когда замечено, что сделано,
что изменить, чтобы не повторилось.

## 9. Безопасность зависимостей

CI на каждый коммит проверяет зафиксированные зависимости (`pip-audit`),
скрипты (`shellcheck`) и собранный образ (`trivy`, уязвимости HIGH и
CRITICAL с исправлением валят сборку). Обновление: `uv lock --upgrade`, затем
полный прогон тестов, включая `tests/golden`.
