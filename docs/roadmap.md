# Roadmap `sav-analytics`

**Актуализировано:** 8 августа 2026 года  
**Базовый снимок:** `main@c8b80fac10667e592239f7930a20a463842a4da7`
**Проверка снимка:** 85 pytest-кейсов проходят, `ruff check .` и P0-mypy проходят.

Этот документ является актуальным планом разработки. `requirements.md` задаёт
продуктовый и методологический контракт, `architecture.md` — целевую архитектуру,
а данный roadmap определяет порядок реализации и критерии завершения этапов.

## 1. Что изменилось относительно прежнего плана

Прототип уже прошёл этап первичной сборки. API разнесён по предметным роутерам,
генератор отчётов — по модулям `core/reporting`, реализованы веса, raking/IPF,
сравнения волн, NPS/CSAT, локальная фоновая подготовка отчёта, прогресс и кэш.
Поэтому декомпозиция `api.py` и `core/report.py` больше не является задачей roadmap.

Главный приоритет теперь — не добавление следующего листа Excel само по себе, а
гарантия, что каждый разрешённый интерфейсом сценарий даёт корректный,
воспроизводимый и явно проверяемый результат. До корреляций нужен короткий P0:

- унифицировать семантику SPSS multiple-response во всех расчётах;
- исправить базы сгруппированных вопросов;
- запретить молчаливое формирование пустых блоков для пока не поддержанных типов;
- поставить обязательные CI, golden и end-to-end проверки;
- связать готовый артефакт с конкретной ревизией конфигурации.

## 3. Методологические инварианты

Эти правила не меняются без отдельного изменения `requirements.md`, независимой
статистической проверки и новых golden-тестов.

1. В режиме, который в интерфейсе может называться «подгруппа vs Total», фактически
   сравниваются непересекающиеся выборки `Subgroup` и `Rest = Total − Subgroup`.
   Total остаётся описательной колонкой, а не второй пересекающейся группой теста.
2. Для долей применяется двусторонний pooled two-proportion z-test. Он выполняется
   только при ожидаемой частоте не меньше 5 во всех четырёх ячейках; иначе тест
   пропускается с причиной в `statistics.txt`. Fisher fallback не применяется.
3. Для средних применяется двусторонний Welch t-test без предположения равных
   дисперсий. Медианы, min/max, SD и SE между группами не тестируются.
4. Порог малой базы проверяется по невзвешенному `N`; для допуска взвешенного теста
   дополнительно используется эффективная база Киша. Взвешенные p-value явно
   маркируются как приближённые.
5. Bonferroni, если включён, применяется внутри определённого семейства сравнений.
   Решения принимаются по значениям полной точности, округление относится только к
   отображению.
6. Любой новый аналитический метод принимается только вместе с прозрачной фикстурой,
   независимым эталоном, проверкой XLSX и полным аудитом в `statistics.txt`.

## 4. Порядок разработки

### P0. Корректность и release gate

**Цель:** убрать сценарии молчаливо неверных чисел и сделать текущий baseline
безопасной основой для дальнейших функций.

**Статус:** выполняется в ветке `codex/p0-correctness`. P0.1 реализует единый
`counted_value` для dichotomy MR, построчные базы grouped-вопросов, SPSS user-missing
для NPS/CSAT и явную блокировку незавершённых типов. В P0.2 уже добавлены проверка
ссылочной целостности, optimistic locking по ревизии конфигурации, типизированный
контракт с отдельной `schema_version`, immutable-артефакты и безопасный API-контракт
`error_code`/`request_id`. Job и download теперь привязаны к
`configuration_revision`/`cache_key`/`artifact_id`; скачивание не запускает расчёт.
В P0.3 добавлен базовый CI с branch coverage 80%, инкрементальным mypy и Docker smoke,
а зависимости зафиксированы в `uv.lock`. Base R golden теперь покрывает обычные и
взвешенные z/Welch, Subgroup-Rest и NPS balance; сквозные golden cases проверяют MR
`counted_value=2` и SPSS user-missing `99`. Полный SAV → API → immutable XLSX/TXT smoke
также работает. Следующий срез — goldens для волн и расширенного NPS/CSAT pipeline,
затем настоящий браузерный smoke.

#### P0.1. Единая модель данных и расчётов

- Ввести явную модель multiple-response: dichotomy/categorical encoding,
  `counted_value`, допустимые коды и правило базы.
- Использовать одну семантику выбора в importer, preview, filters, bases, report и
  statistics audit; убрать расхождение `value == 1` против `value != 0`.
- Считать базу grouped multiple/matrix построчно: `any valid` для валидной базы и
  `all missing` для пропуска, а не через `max/min` агрегатов элементов.
- Исключать SPSS user-missing из проверки диапазона NPS/CSAT и из расчётной базы.
- До полноценной реализации блокировать назначение `multiple_choice_categorical` и
  `ranking` с понятным сообщением. Ни один разрешённый тип не должен создавать
  пустой блок отчёта без ошибки.

#### P0.2. Целостность конфигурации и артефакта

- Ввести типизированную сохраняемую модель проекта и отдельную версию её схемы. **Реализовано.**
- Проверять ссылки между recodings, filters, banners и weights; блокировать удаление
  используемого объекта либо выполнять явную согласованную замену.
- Добавить ревизию конфигурации и optimistic locking, чтобы параллельные изменения
  не перезаписывали друг друга молча.
- Привязать job и скачивание к `configuration_revision`, `cache_key` и неизменяемому
  идентификатору артефакта. Download endpoint не должен строить новый отчёт при
  cache miss или после изменения настроек. **Реализовано.**
- Добавить безопасные пользовательские коды ошибок; traceback оставлять только в
  серверном структурированном логе с request/job ID. **Реализовано.**

#### P0.3. Автоматические ворота качества

- Добавить CI для Ruff, pytest, coverage, type checking, Docker build и boot smoke.
  **Базовый gate реализован; type checking пока охватывает P0-контракты.**
- Зафиксировать зависимости воспроизводимым lock-файлом. **Реализовано через `uv.lock`.**
- Создать независимые синтетические SAV/SPSS/R golden fixtures: MR с
  `counted_value != 1`, complementary missing, user-missing `99`, single, scale,
  numeric, matrix, веса, волны, NPS и CSAT. **Реализованы Base R cases для обычных и
  взвешенных z/Welch, Subgroup-Rest и NPS balance, а также pipeline cases для MR
  `counted_value=2` и SPSS user-missing `99`; волны и расширенный NPS/CSAT остаются
  в работе.**
- Проверять не только отдельные формулы, но и полный `statistics.txt`, числовые
  значения/структуру XLSX и причины каждого пропущенного теста. **Полный нормализованный
  SHA `statistics.txt` и структура immutable XLSX добавлены для базового pipeline.**
- Добавить браузерный smoke: upload → structure → recoding → filter → banner/weight
  → prepare → download → проверка XLSX/TXT.
- Добавить тесты повреждённого cache, dangling references, конкурентной записи и
  ошибки фонового задания.

**P0 завершён, когда:**

- все типы, доступные в UI, либо полностью проходят preview/report, либо явно
  недоступны с объяснением;
- MR fixture с `counted_value != 1` одинаково считается во всех подсистемах;
- эталонные значения SPSS/R совпадают в согласованном допуске;
- clean checkout проверяется одной командой, а обязательные checks защищают `main`;
- полный браузерный сценарий и Docker smoke проходят в CI;
- скачивание всегда отдаёт артефакт той ревизии, которую подготовил job.

### P1. Завершение аналитического MVP

**Зависимость:** P0.

1. **Настройка и preflight отчёта**
   - единый экран с вопросами, фильтром, баннером, весом и глобальными правилами;
   - ошибки и предупреждения до запуска;
   - невзвешенная и взвешенная база в Excel;
   - переключатель p-value, полный comments/audit contract;
   - дополнительный знак после запятой, если округление скрывает значимое различие.
2. **Корреляции**
   - необязательный лист `Correlations`;
   - Pearson, Spearman, pairwise base и p-value;
   - правила веса/`n_eff`, малой базы, цветов и лимита 100 переменных строго по
     `requirements.md`;
   - отдельные независимые golden cases.
3. **Волны и raking**
   - выбор, отключение и ручной порядок волн;
   - raking отдельно внутри каждой волны;
   - цели по сохранённым recoding и импорт target distributions из шаблона;
   - goldens для bounds, non-convergence и wave-specific diagnostics.
4. **Полная модель вопроса**
   - ручное создание, изменение состава и разгруппировка multiple/matrix;
   - categorical multiple и обе структуры строгого ranking;
   - item labels, пояснение шкалы и custom Top/Bottom groups;
   - порядок и отключение категорий баннера.

**P1 завершён, когда:** каждый заявленный в MVP тип и необязательный лист проходит
полный путь SAV → UI → preview → XLSX/TXT, имеет независимый golden и не требует
ручного исправления сформированного файла.

### P2. Цельный single-user workflow

**Может идти параллельно с поздней частью P1 после стабилизации API-контрактов.**

- Поиск и сортировка проектов, переименование, дублирование, корзина и восстановление.
- Autosave и локальный Undo/`Ctrl+Z` либо согласованное изменение этого требования.
- Dirty-state protection во всех редакторах.
- Deep link проекта, восстановление выбранного экрана и активного job после reload.
- Каталог баннерных переменных, управление категориями и предупреждение о широком
  баннере.
- Клавиатурная альтернатива drag-and-drop, корректные tabs/dialog focus и
  автоматическая accessibility-проверка.
- Разделить монолитный `static/app.js` по предметным модулям. Решение о React/TS
  принять отдельно; миграция фреймворка сама по себе не является milestone.

**P2 завершён, когда:** аналитик может создать, изменить, проверить и повторно открыть
проект без потери состояния; невозможно оставить висячие зависимости; ключевые
операции доступны с клавиатуры и покрыты Playwright.

### P3. Постоянное хранилище и воспроизводимые версии

**Зависимость:** P0 и стабилизированные контракты затрагиваемых частей P1/P2.
Проектирование адаптеров можно начать раньше, но схему нельзя фиксировать поверх
ещё меняющейся модели вопросов и отчёта.

- PostgreSQL + Alembic для проектов, конфигураций, запусков и версий.
- Repository interfaces вместо прямой привязки доменного кода к `project.json`.
- Защищённый файловый том или S3-compatible `ArtifactStore` для SAV и артефактов.
- Мигратор существующих локальных проектов с проверкой на копии данных.
- Неизменяемые версии конфигураций и отчётов: source SHA-256, schema/core/dependency
  versions, автор, время, параметры и checksums итоговых файлов.
- Retention, корзина и безопасное окончательное удаление связанных данных.

**P3 завершён, когда:** два API-инстанса не теряют параллельные изменения, restart не
теряет метаданные, а любой сохранённый отчёт однозначно связан с воспроизводимым
снимком исходника и конфигурации.

### P4. Авторизация и многопользовательский pilot

**Зависимость:** P3.

- Уточнить модель доступа из требований: общая команда аналитиков, admin/user,
  владелец и видимость проектов.
- Серверные сессии или OIDC; защищённые cookies, CSRF и проверка прав на каждом
  project/artifact endpoint.
- Audit log входов, изменений, чтения исходного SAV и скачивания отчётов.
- Reverse proxy, HTTPS, request-body limits, security headers и строгая CSP.
- Self-host шрифтов и отсутствие внешних запросов со страницы проекта.

**P4 завершён, когда:** кроме health/login нет анонимного доступа к данным, матрица
прав покрыта integration tests, а действия с исходниками и артефактами аудируются.

### P5. Надёжные фоновые задания

**Зависимость:** P3; может идти параллельно с P4.

- Redis и отдельные workers; PostgreSQL остаётся источником истины статусов.
- Идемпотентность по версии конфигурации, retries, timeout, cancel, TTL и cleanup.
- Восстановление job после перезапуска API/worker и сохранение статуса в UI.
- Download только готового immutable artifact конкретного job.
- Ограничения параллелизма, памяти и диска; нагрузочные тесты двух тяжёлых отчётов.

**P5 завершён, когда:** перезапуск не теряет job, два одинаковых prepare не дублируют
расчёт, зависшая задача завершается по timeout, а HTTP workers не выполняют тяжёлый
report build.

### P6. Production operations

**Зависимость:** P0, P3, P4 и P5.

- Non-root images, health/readiness checks, restart policy и resource limits.
- CI/CD со staging, миграциями и контролируемым rollback.
- Метрики import/report duration, queue depth, failures, cache hit rate и storage;
  dashboards, alerts и структурированные логи с request/job ID.
- Бенчмарки на типовом, 10 000-строчном и широком SAV; целевой типовой отчёт — не
  более 120 секунд после устранения алгоритмических узких мест.
- Ежедневные шифрованные off-host backups; RPO не более 24 часов, RTO не более
  4 часов; ежемесячное документированное тестовое восстановление.
- Security scan зависимостей/образов, runbook инцидентов и проверка удаления данных.

**P6 завершён, когда:** staging повторяет production-контур, развёртывание и rollback
проверены, сбой worker вызывает alert, а backup действительно восстанавливается.

## 5. Зависимости и параллельная работа

```text
 ├── P1 Аналитический MVP ──┐
 ├── P2 Single-user UX ─────┼── P3 Постоянные версии ──┬── P4 Auth

```

P1 и P2 можно вести параллельно только после фиксации контрактов P0. P4 и P5 можно
вести параллельно после появления устойчивых идентификаторов и версий в P3.

## 6. Ближайшая очередь задач

1. MR `counted_value` и единая семантика selected/not selected.
2. Построчная база multiple/matrix и user-missing для NPS/CSAT.
3. Явный запрет незавершённых `ranking` и categorical multiple.
4. Referential integrity recoding/filter/banner/weight.
5. Configuration revision и артефакт конкретного job.
6. CI, lock-файл и clean-install/Docker smoke.
7. Независимый golden pack SPSS/R + полный snapshot `statistics.txt`/XLSX.
8. Полный Playwright smoke аналитического workflow.
9. Единый report preflight и недостающие настройки вывода.
10. Лист `Correlations`.

Пункты 1–8 образуют обязательный P0 и не должны вытесняться новой аналитической
функцией.

## 7. Definition of Done для каждого аналитического изменения

- Формула, база, missing policy, вес и семейство множественных сравнений описаны.
- Есть маленькая прозрачная фикстура с ручной проверяемостью и независимый эталон.
- Проверены невзвешенный и, где применимо, взвешенный сценарии.
- Проверены основная, фильтровая, малая/пустая база и причина неприменимости теста.
- Результат согласован между preview, XLSX и `statistics.txt`.
- В `statistics.txt` нет данных отдельных респондентов.
- API validation, unit/integration test и browser workflow обновлены.
- README, capability matrix и требования не противоречат реализации.
