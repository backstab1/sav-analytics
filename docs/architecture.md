# Техническая архитектура sav-analytics

Статус: рекомендуемая архитектура MVP. Она рассчитана на внутреннюю команду до пяти одновременно работающих аналитиков, 40–50 новых проектов в год, бессрочное хранение проектов и целевое время формирования типового отчёта не более 1–2 минут.

## 1. Архитектурные принципы

- Статистическая точность и воспроизводимость важнее преждевременной оптимизации.
- Веб-запросы не выполняют тяжёлые расчёты: отчёты формируются фоновыми процессами.
- Исходный SAV неизменяем; настройки, производные переменные и отчёты версионируются отдельно.
- Расчётное ядро отделено от веб-интерфейса и может тестироваться без запуска сервера.
- Один production-сервер и Docker Compose достаточны для MVP; Kubernetes не требуется.
- Данные и подписи SAV не отправляются во внешние AI-сервисы.

## 2. Рекомендуемый стек

### 2.1. Интерфейс

- React и TypeScript;
- Vite для локальной разработки и production-сборки;
- клиентская маршрутизация и библиотека запросов к API;
- поддерживаемые браузеры: актуальные Chrome, Edge и Яндекс Браузер.

Все три браузера основаны на Chromium, поэтому отдельные реализации интерфейса для них не требуются. Основные пользовательские сценарии покрываются автоматическими браузерными тестами.

### 2.2. API и расчётное ядро

- Python;
- FastAPI для HTTP API;
- Pydantic для валидации конфигураций;
- SQLAlchemy и миграции Alembic для работы с PostgreSQL;
- отдельный пакет `analytics_core` без зависимости от веб-слоя.

Python выбран потому, что импорт SAV, статистические методы и создание Excel удобно собрать в одном проверяемом расчётном контуре.

### 2.3. Обработка данных и Excel

- Pyreadstat для чтения SAV и метаданных SPSS;
- pandas, NumPy и SciPy как базовый вычислительный стек;
- statsmodels только для методов, которым нужна его проверенная реализация;
- XlsxWriter для формирования XLSX с форматированием, ссылками, примечаниями и закреплением областей.

Pyreadstat не считается самостоятельно валидированным статистическим продуктом, поэтому импорт данных и метаданных обязательно проверяется на эталонных SAV. Критические расчёты реализуются в `analytics_core` и сверяются с заранее подготовленными результатами SPSS и согласованными тестовыми файлами.

### 2.4. Фоновые задачи

- Celery как очередь задач;
- Redis как брокер коротких сообщений и хранилище оперативного состояния задач;
- PostgreSQL остаётся источником истины для статусов и результатов заданий.

В Redis передаются только идентификаторы задач, а не содержимое SAV. Фоновый worker загружает нужный файл из защищённого хранилища, создаёт временную рабочую директорию, выполняет расчёт и сохраняет итоговые артефакты.

### 2.5. Хранение

- PostgreSQL хранит пользователей, проекты, конфигурации, статусы, версии отчётов и ссылки на файлы;
- SAV, XLSX, `statistics.txt` и выгрузки весов хранятся как файлы в отдельном защищённом томе;
- слой хранения имеет внутренний интерфейс, чтобы позже заменить локальный том на S3-совместимое объектное хранилище без переделки расчётного ядра;
- имя файла на диске генерируется приложением; исходное пользовательское имя хранится только как метаданные;
- для каждого артефакта сохраняются размер и SHA-256.

## 3. Компоненты

```text
Browser
   │ HTTPS
Reverse proxy
   ├── Frontend
   └── FastAPI
         ├── PostgreSQL
         ├── Protected file storage
         └── Redis → Celery workers → analytics_core → XLSX/TXT
```

Рекомендуемые production-контейнеры:

1. `proxy` — HTTPS и маршрутизация;
2. `frontend` — статическая сборка React;
3. `api` — FastAPI;
4. `worker` — два независимых процесса расчёта;
5. `postgres`;
6. `redis`;
7. `backup` — плановые резервные копии и проверка срока хранения.

## 4. Сервер

### 4.1. Рекомендуемая production-конфигурация

- Linux, предпочтительно актуальный Ubuntu LTS;
- 8 быстрых vCPU;
- 32 ГБ RAM;
- 500 ГБ NVMe SSD;
- сетевой канал от 1 Гбит/с;
- отдельное внешнее хранилище резервных копий объёмом не менее 500 ГБ.

Это стартовая конфигурация с запасом для двух параллельных отчётов и пяти пользователей. Для пилота допустимы 4 vCPU, 16 ГБ RAM и 200 ГБ SSD, но такая конфигурация не принимается как гарантия целевого времени 1–2 минуты.

API запускается в двух процессах. Очередь расчётов по умолчанию исполняет не более двух тяжёлых задач одновременно, чтобы один широкий отчёт не вытеснил базу данных и веб-интерфейс из памяти. Число процессов меняется после бенчмарка.

### 4.2. Проверка производительности

Целевое время `≤ 120 секунд` измеряется от старта фоновой задачи до сохранения готовых XLSX и `statistics.txt`. Время ожидания задачи в очереди показывается отдельно.

До production-развёртывания создаются три эталонных набора:

1. небольшой обычный SAV;
2. SAV на 10 000 строк с реалистичным числом переменных;
3. широкий стрессовый SAV с максимальным баннером, тестами, весом и корреляциями.

Для каждого этапа отдельно измеряются импорт, подготовка переменных, расчёты, тесты и запись Excel. Если типовой отчёт превышает 120 секунд, сначала профилируется код; масштабирование до 16 vCPU и 64 ГБ рассматривается только после устранения алгоритмических узких мест.

## 5. Безопасность и доступ

- Самостоятельной регистрации нет; пользователей создаёт администратор.
- Пароль восстанавливается через администратора.
- Все авторизованные аналитики видят все проекты.
- Пароли хранятся только как Argon2id-хэши.
- Авторизация использует серверную сессию и защищённую cookie `HttpOnly`, `Secure`, `SameSite`.
- После появления домена production работает только по HTTPS; доступ по открытому HTTP не допускается.
- Загружаемые файлы проверяются по расширению, сигнатуре и успешности чтения как SAV; они никогда не исполняются.
- Секреты и пользовательские данные не попадают в Git и журналы приложения.
- В журналах хранятся технические события, идентификаторы проектов и ошибки без строк респондентов.

Пока домена нет, разработка ведётся локально. Для production необходимо приобрести домен или выделить внутреннее DNS-имя и выпустить TLS-сертификат до предоставления доступа пользователям.

## 6. Жизненный цикл данных

- Активные проекты, исходные SAV и отчёты хранятся бессрочно.
- Удалённый проект попадает в корзину на 30 дней.
- До истечения 30 дней администратор может восстановить проект.
- После окончательного удаления удаляются SAV, отчёты, производные файлы и метаданные проекта; событие удаления остаётся в техническом журнале без содержимого данных.
- Отчёты неизменяемы и привязаны к снимку конфигурации, версии расчётного ядра и SHA-256 исходного SAV.

## 7. Резервное копирование

- Ежедневная резервная копия PostgreSQL и файлового хранилища;
- хранение ежедневных копий не менее 14 дней;
- копии находятся вне основного сервера;
- резервная копия шифруется;
- не реже одного раза в месяц выполняется тестовое восстановление;
- backup считается успешным только после проверки целостности архива и записи результата в журнал.

## 8. Локальная разработка и развёртывание

Локально все сервисы запускаются через Docker Compose. Frontend и backend могут работать в режиме горячей перезагрузки, а PostgreSQL, Redis и файловое хранилище используют локальные development-тома.

Production использует те же собственные Docker-образы, собранные из зафиксированных зависимостей. Развёртывание выполняется через GitHub Actions после прохождения тестов, но production-секреты хранятся только на сервере или в защищённом хранилище CI.

## 9. Проверка точности

Для каждого поддерживаемого типа вопроса создаются маленькие прозрачные фикстуры, где результат можно проверить вручную. Отдельные золотые тесты покрывают:

- чтение labels, value labels и missing values SAV;
- single, multiple, scale, numeric, ranking и matrix;
- Main и Filter базы;
- перекодировки и сложные фильтры;
- Total/Rest, допустимый по ожидаемым частотам z-test и Welch t-test;
- Bonferroni и малые/эффективные базы;
- готовые и рассчитанные веса;
- волны, NPS, CSAT и корреляции;
- точную структуру XLSX и `statistics.txt`.

Числовые результаты сравниваются с эталонными значениями до заданного допуска. XLSX дополнительно проверяется как структура: листы, числовые типы, форматы, ссылки, примечания, закреплённые области и цвета.

## 10. Roadmap

Актуализировано 2 августа 2026 года. Статусы отражают состояние рабочего прототипа, а не только наличие отдельных модулей.

| Этап | Статус | Реализовано | Осталось |
| --- | --- | --- | --- |
| 1. Каркас и инфраструктура | Частично | Локальное FastAPI-приложение, файловое хранилище проектов и Docker Compose | PostgreSQL, авторизация, роли и управление пользователями |
| 2. Проекты и импорт SAV | Готово | Загрузка и проверка SAV, неизменяемый оригинал, SHA-256, метаданные, повторное распознавание и библиотека проектов | Поддерживать регрессионными тестами |
| 3. Модель вопросов | Почти готово | Ручные настройки, специальные ответы, multiple, matrix, перекодировки и порядок вопросов | Ручное создание логических вопросов и разгруппировка автоматически найденных структур |
| 4. Баннеры, базы и фильтры | Готово | Обычные и вложенные баннеры, проектные перекодировки, пользовательские базы, общий фильтр и вложенные условия | Поддерживать регрессионными тестами |
| 5. Статистическое ядро | Готово | Subgroup/Rest, попарные тесты, z-test, Welch t-test, Bonferroni, малые и эффективные базы, доверительные интервалы и аудит | Расширять золотые фикстуры вместе с новыми методами |
| 6. Отчёты и выполнение задач | Почти готово | XLSX, `statistics.txt`, фоновая локальная задача, прогресс и кэш согласованного комплекта артефактов | Постоянная очередь, история и версионирование отчётов, восстановление задач после перезапуска |
| 7. Расширенная аналитика | Почти готово | Готовые веса, raking/IPF, эффективная база Киша, сравнение волн, NPS и CSAT | Корреляции; выбор и порядок волн; raking внутри волн; цели по проектным перекодировкам |
| 8. Production | Не завершён | Базовая проверка загрузок, исключение исследовательских данных и секретов из Git, локальные контейнеры | Бенчмарки, защищённое файловое хранилище, HTTPS, резервное копирование, мониторинг, CI/CD и production-развёртывание |

### 10.1. Ближайший порядок разработки

1. **Корреляции:** лист `Correlations`, Pearson и Spearman, парные базы, p-value, цветовая маркировка и золотые тесты.
2. **Волны и веса:** ручной выбор и порядок волн, raking отдельно внутри волн и цели по сохранённым проектным перекодировкам.
3. **Редактор структуры:** ручное создание логического вопроса, объединение и разгруппировка multiple/matrix без изменения исходного SAV.
4. **Постоянная платформа:** PostgreSQL, пользователи, роли, серверные сессии и защищённое хранение файлов.
5. **Надёжное выполнение отчётов:** Redis, отдельные worker-процессы, история версий и восстановление незавершённых задач.
6. **Выход в production:** эталонные бенчмарки, security-проверки, резервные копии с тестовым восстановлением, мониторинг и CI/CD.

Каждый пункт завершается работающим вертикальным срезом, автоматическими тестами и обновлением README. Переход к следующему пункту не должен скрывать ошибки расчётов или ухудшать воспроизводимость уже реализованных отчётов.
