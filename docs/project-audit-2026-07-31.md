## Краткий вывод

Проект находится в хорошем состоянии для рабочего локального прототипа: реализован цельный путь от загрузки SAV до скачивания Excel и текстового статистического аудита, а критичная расчётная логика покрыта автоматическими тестами. На момент аудита успешно выполняются **58 тестов** и `ruff check .`.

Главный разрыв между текущим состоянием и production — не в аналитических возможностях, а в эксплуатации: хранение на локальном диске, отсутствие пользователей и разграничения доступа, процессная (не постоянная) очередь отчётов и отсутствие CI/CD/наблюдаемости. До публикации приложения для нескольких пользователей стоит закрыть эти риски прежде, чем расширять перечень аналитических модулей.

## Что уже сделано хорошо

- Слой расчётов разнесён по предметным модулям: SAV-импорт, определение структуры, перекодировки, фильтры, баннеры, взвешивание, статистика и генерация отчёта.
- API использует FastAPI и Pydantic-валидацию; ограничения на размер файлов и ключевые поля заданы на входе.
- Загрузка SAV устроена аккуратно: имя нормализуется, размер ограничивается, считается SHA-256, чтение/инспекция происходят до публикации нового проекта.
- Обновление `project.json` и артефактов отчёта использует временные файлы и атомарную замену, что снижает риск частично записанного файла при сбое.
- Есть кэш отчётов, зависящий от хэша источника и конфигурации, а также защита от параллельного построения одинакового отчёта внутри одного процесса.
- Покрыты наиболее рискованные вычисления: взвешивание, статистические тесты, SAV-reader, перекодировки, фильтры, баннеры, API и структура XLSX.
- Docker-конфигурация минимальна и понятна; данные вынесены в volume.
- README честно отделяет готовые возможности от отложенных и содержит способ запуска и проверки.

## Предлагаемый план

### Этап 1 — стабилизация прототипа (1–2 недели)

1. Добавить GitHub Actions/аналог CI: тесты, Ruff, типизация, coverage и Docker build.
2. Добавить структурированное логирование и корреляционные ID для HTTP-запроса и отчётной задачи.
3. Ввести e2e smoke-тест: загрузка тестового SAV → настройка → подготовка → скачивание и валидация XLSX.
4. Установить ограничение времени/памяти для построения отчёта и максимальный срок хранения кэша.
5. Декомпозировать `api.py`, не меняя внешний API; начать с маршрутов reports и weights.

### Этап 2 — готовность к нескольким пользователям (2–4 недели)

1. Определить модель доступа: владелец проекта, организация/команда, роли «просмотр», «редактирование», «администратор».
2. Внедрить аутентификацию через корпоративный SSO/OIDC и аудит операций с проектом/выгрузками.
3. Перенести метаданные в PostgreSQL, файлы — в S3-совместимое хранилище; написать миграцию существующих локальных проектов.
4. Заменить внутрипроцессные jobs на устойчивую очередь и обеспечить дедупликацию расчётов по cache key.
5. Настроить резервные копии, retention политики и удаление проекта вместе с производными артефактами.

### Этап 3 — надёжность расчётов и развитие продукта (после этапа 2)

1. Сформировать набор эталонных SAV/XLSX-кейсов и golden-тесты: граничные базы, пропуски, multiple response, веса, волны, NPS/CSAT.
2. Добавить версионирование конфигурации и отчётов: кто, когда и что изменил; возможность воспроизвести выгрузку.
3. Добавить мониторинг: время чтения SAV, длительность расчёта, ошибки по типам, размер очереди, cache hit rate.
4. Приоритизировать следующие аналитические функции по реальным сценариям пользователей; CBC/MaxDiff/CSI не начинать до подтверждения спроса и утверждения методики.

## Техническая целевая схема

```text
Browser
  │ HTTPS + OIDC
  ▼
Reverse proxy ──► FastAPI (stateless API) ──► PostgreSQL (projects/config/jobs/audit)
                              │
                              ├──────────────► Object storage (SAV/XLSX/statistics)
                              │
                              └──────────────► Redis + worker queue ──► report workers
```

Такое разделение позволяет безопасно масштабировать API и воркеры независимо, переживать перезапуски, сохранять историю и ограничивать доступ к данным.

## Критерии готовности к production

- Все запросы требуют аутентификации; проверка прав присутствует на каждом проектном endpoint.
- Метаданные, задания и аудит не теряются при рестарте и при двух экземплярах API.
- Отчёт воспроизводим по версии входного SAV и версии конфигурации.
- Есть CI с обязательными проверками и артефактами покрытия/интеграционных тестов.
- Есть резервное копирование и проверенная процедура восстановления.
- Есть метрики, журналы и оповещение о неуспешных заданиях.
- Тяжёлые расчёты ограничены ресурсами и не блокируют API.
